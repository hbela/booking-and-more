# 1. What was actually wrong

Nothing was broken. The application had simply never had a design pass, and what stood in for one had
started to cost something:

- **Four colour tokens, teal, described in their own comment as a placeholder.** Everything else was stock
  Tailwind `slate-*`, spelled out at each of 294 call sites.
- **No fonts at all** — the default `system-ui` stack, on a product whose default language is Hungarian.
- **No component library.** The design system was three exported *strings* — `inputClass`, `buttonClass`,
  `secondaryButtonClass` — at the bottom of a 547-line feature file, imported by 14 others. Composition was
  string interpolation, so `` `${inputClass} max-w-sm` `` worked only by luck of declaration order.
- **Three separate `Section` implementations and two incompatible `Field`s**, one per feature file that
  needed one.
- **Dark mode was a media query**, with 166 hand-written `dark:` variants and no way for a visitor to
  choose.
- **`clsx`, `tailwind-merge` and `lucide-react` were installed and never imported.** No icon appeared
  anywhere in the product.
- **`public/` contained two files**: a teal icon and a manifest. There was no imagery layer.

# 2. The decisions

## 2.0 The Stitch project

`projects/13796210681603381949` — "Booking and More — Cobalt", holding two design systems:

| | asset | mode | seed |
|---|---|---|---|
| **Cobalt Day** | `assets/5906614718078353848` | `LIGHT` | `#1f5cd4` |
| **Cobalt Night** | `assets/8917453693549482204` | `DARK` | `#6f9ff7` |

Both carry a full `designMd` — Material-3 token names in YAML front-matter, a typography scale, a spacing
map, and prose covering brand, colour, type, layout, elevation, shape, per-component rules and
accessibility. That prose is the actual specification the hand-rebuild follows; the generated screens are
illustrations of it.

Two practical notes for whoever generates more screens:

1. **The MCP call reliably times out and the screen still arrives.** Generation takes longer than the
   client will wait. Do not retry on timeout — poll `list_screens` a few minutes later. Retrying starts a
   second generation; that is how this project ended up with two near-identical booking screens.
2. **Stitch does generate imagery**, contrary to what the `stitch-ui-design` and `stitch-loop` skills say.
   Asking for a hero band produced a standalone abstract image asset alongside the screen, which is where
   `public/hero-booking.jpg` came from. No separate image model was needed.

The earlier `projects/32805612233801258` ("Soft Premium Booking Experience", plum `#4a154b`, rose
secondary, warm ivory) is the rejected direction. Its DESIGN.md *structure* was forked; its palette and
compositions were not — those layouts were composed for a warm plum, and reading them as the spec for a
cobalt product would import decisions nobody made.

## 2.1 Stitch is the specification, never the shipped code

Stitch generates HTML and a screenshot. That HTML carries no `next-intl` keys, no server components, no
form wiring, and none of the accessibility decisions recorded across the phase documents (§2.6). Pasting it
in would mean re-deriving all four, per screen, while inheriting class soup that diverges from the token
layer.

So the pipeline is: Stitch screen → design tokens → `globals.css` + `components/ui/` → hand-written JSX.
**No file under `.stitch/` or generated by Stitch is ever imported by the application.**

## 2.2 Two colour ramps, not one

PRD §9.1 specifies per-tenant white-label branding — a tenant supplies a logo and brand colours, and their
booking page wears them. That is not being built here. But baking one blue into every screen would make it
a rewrite when it is.

So there are two ramps:

- **`--color-brand-*`** — the product's own deep blue. Dashboard, platform admin, onboarding, billing,
  marketing, auth. Fixed; a tenant never changes it.
- **`--color-accent-*`** — the public booking page at `/{tenantSlug}/book`. Identical values today, and the
  booking page is wrapped in an element that sets `--accent` from a variable rather than reading the ramp
  directly. When §9.1 arrives it is a data change: read the tenant's hex, set it on that wrapper.

**Product chrome must never reference `accent-*`, and the booking page must never reference `brand-*`.**
That is the whole discipline; if the two are mixed the split has bought nothing.

One requirement recorded here rather than discovered later: **when a tenant-supplied hex does become
`--accent`, it must be contrast-checked server-side first.** A tenant is perfectly capable of choosing a
pale yellow and making their own booking button unreadable.

## 2.3 The colour itself

Deep blue at **oklch hue 262**, anchored on `brand-600 = oklch(0.512 0.196 262)` ≈ `#1f5cd4`. Hue 262 reads
as corporate blue; the more obvious hue ≈258 at this lightness renders closer to an electric cobalt that
fights with every status colour next to it.

The neutral ramp is re-tinted to the **same hue** at chroma ≤ 0.033, so greys sit under the blue rather than
beside it, and is declared as **`--color-slate-*`, deliberately shadowing Tailwind's own slate**. That is
not cosmetic — it is what makes the migration safe (§2.5).

Two results worth carrying:

- **`brand-500` on white is 3.95 — it fails AA and must never carry text.** Fills and rings only. It is the
  one stop on the ramp that looks usable and is not.
- **The dark-mode primary button inverts** — `brand-400` background with `slate-950` text — rather than
  dimming the light-mode button. A darkened blue with white text cannot reach 4.5:1 against a dark surface
  at any chroma worth having.

Status colours are `danger` `oklch(0.505 0.205 27)`, `success` `oklch(0.500 0.120 155)`, `warning`
`oklch(0.500 0.100 75)` in light, all ≥ 5.5:1 on white. **The success and warning chromas are 0.120 and
0.100 rather than the rounder 0.130 and 0.120 because those fall outside sRGB**: the browser would clip
them, so the stored value would no longer describe what renders, and the contrast test would be asserting
against a colour nobody sees.

### 2.3.1 `--line` and `--line-strong` are two different promises

Found while writing the contrast test, and worth recording because the obvious palette is wrong.

The neutral ramp's `slate-300` is the natural "border" colour and reaches **1.50:1 on white**. That is fine
for a card edge or a row divider, which WCAG asks nothing of — they separate content, and losing them
loses nothing but tidiness.

It is not fine for the edge of a **control**. WCAG 2.1 **1.4.11 Non-text Contrast** requires 3:1 for the
visual boundary that tells you where an input or a secondary button *is*, and a text field whose only
affordance is a 1.5:1 hairline is a field some people cannot find.

So the two tokens carry different obligations, and `--line-strong` is not the next step down the ramp:

| | light | dark |
|---|---|---|
| `--line` — separators, card edges | `slate-200` | `oklch(0.31 0.03 262)` |
| `--line-strong` — control boundaries | `oklch(0.64 0.028 262)` = `#838d9e` (3.36:1 on white, 3.21:1 on raised) | `oklch(0.52 0.032 262)` = `#5f697c` (3.35:1 on surface, 3.03:1 on raised) |

Both clear 3:1 against the raised surface as well as the plain one, because a field inside a card is the
common case. The result reads heavier than a fashionable hairline border. That is the requirement, not an
accident, and it should not be "softened" later.

## 2.4 Three CSS mechanisms, in order

`@theme` holds the static ramps — compile-time constants, nothing flips. Then:

**`@custom-variant dark`, with two branches.** There are three states and a bare media query gets two of
them wrong:

| attribute | OS | wanted |
|---|---|---|
| none | dark | dark — media branch |
| `data-theme="light"` | dark | light — the media branch must *not* fire |
| `data-theme="dark"` | light | dark — the media branch *cannot* fire |

Hence a guarded media branch plus an attribute branch. Both wrapped in `:where()` so they stay at zero
specificity and a `dark:` utility never outranks a plain one by accident.

**`@theme inline` for the semantic tokens.** `inline` is the load-bearing word. Without it, `bg-surface`
compiles to `background-color: var(--color-surface)`, `--color-surface` is pinned at `:root`, and
redefining it deeper in the tree does nothing. With it, Tailwind substitutes the reference textually —
`bg-surface` becomes `background-color: var(--surface)` — so any ancestor that redefines `--surface` wins.
That is both how the theme flips and how §2.2's booking-page wrapper will take a tenant's accent.

Two things that are cheap to get right and expensive to debug:

- **`color-scheme` must resolve to `light` or `dark`, never the previous `light dark`.** With `light dark`,
  the native `<select>` in `locale-switcher.tsx` — a deliberate accessibility choice (§2.6) — along with
  scrollbars and date inputs, follows the operating system regardless of the visitor's choice. It is the
  most visible bug this architecture can ship.
- **The dark declarations are duplicated** between the media block and the `[data-theme="dark"]` block.
  CSS cannot attach one block to both a media query and a bare selector, and aliasing through a second
  variable layer trades twelve literals for twelve indirections without removing the duplication. It is
  deliberate. §4.1's contrast test reads both blocks and fails if they drift.

## 2.5 Why the migration cannot be half-done

Because `--color-slate-*` is **redefined rather than replaced**, the token commit lands alone and every one
of the 294 existing `slate-*` classes re-tints to the blue neutral immediately, with no component touched.
Nothing was migrated, so nothing can be half-migrated.

Screens then convert one at a time — `bg-white dark:bg-slate-950` → `bg-surface`, `text-slate-600
dark:text-slate-400` → `text-ink-muted`. Since the slate ramp and the semantic tokens resolve to the same
colours, **a converted screen and an unconverted one are pixel-identical**. There is no visual seam at any
commit boundary. The `--color-slate-*` block is deleted last, once the grep is empty.

## 2.6 What must not be "improved"

Each of these has written rationale in an earlier phase record. A redesign is exactly the moment somebody
reverses one without noticing there was a decision:

- **Gated navigation items are `<span aria-disabled>`, never dimmed anchors.** An anchor stays focusable and
  activates on Enter however it is painted, so a "disabled" one navigates to a screen that 403s
  (phase-9 §2.11).
- **There is no `Dialog` primitive and there is not going to be one.** `useEditPanel` substitutes an inline
  panel plus an explicit focus contract — the panel takes focus on open and hands it back on close.
- **`role="note"` on `Notice`, `role="alert"` on `ErrorText`.** A prerequisite is not an error and must not
  interrupt.
- **The locale switcher is a native `<select>`.** A custom dropdown is a worse control for a keyboard and
  screen-reader user, not a better-looking one.
- **`aria-current="page"` is what a screen reader announces**; the underline is only its visual echo.

## 2.7 The library lives in the app, not in a package

`apps/web/src/components/ui/`, not `packages/ui`. Three reasons, all specific to this repo:

1. Every package here is consumed through its `exports` map resolving to `dist/`, so each needs a
   `tsc --watch`. That is already 11 persistent tasks with `turbo.json`'s concurrency raised above its
   default of 10 — and CLAUDE.md's Layout section records exactly what a stale `dist/` does to Turbopack.
2. These are `"use client"` components. Compiling them to `dist/` and consuming that from Turbopack is that
   failure mode, and Tailwind v4 would additionally need `@source` pointed at compiled output.
3. There is one consumer. `apps/api` and `apps/worker` render email HTML, not React.

**Revisit at the second consumer** — a marketing site or a separate customer portal.

### 3.1 What increments 1 and 2 actually changed

Worth stating plainly, because the diff is small and the effect is not.

**Increment 1 touched no component file.** It rewrote `globals.css`, added
`lib/{cn,theme-preference,theme-script,use-edit-panel}.ts`, wired `next/font`, and added the theme script
to the two documents. Because `--color-slate-*` is redefined rather than replaced, and because
`@custom-variant dark` compiles every existing `dark:` utility into *both* a guarded media branch and an
attribute branch, all 294 `slate-*` classes and all 166 `dark:` classes across the 23 untouched components
re-tinted and became toggle-aware at once. Verified in the compiled CSS:

```css
.dark\:border-slate-700:where(:not([data-theme=light],[data-theme=light] *)){…}  /* inside @media */
.dark\:border-slate-700:where([data-theme=dark],[data-theme=dark] *){…}          /* outside it   */
```

**Increment 2 changed no call site.** It added `components/ui/*` and replaced the eight component
definitions and three class-name constants in `dashboard-shell.tsx` with re-exports and recipe-derived
constants. Every one of the fourteen importers still compiles unchanged, and every button, input, card,
callout and row action in the product took the new styling in that one commit.

Both increments end green on `lint`, `check-types`, `test` and `build`, and the build still reports the
locale routes as **SSG** — confirming the theme script did not cost static rendering, which was the entire
reason for not reading the cookie in the layout.

### 3.3 The booking flow was restyled, not restructured

The plan called for splitting `booking-flow.tsx` into six presentational children behind a
characterisation test, so the restyle diff would be readable. **That was not done, deliberately.**

Reading the file settled it: every piece of styling there is a `className` string, with no logic
entangled in any of them. So the restyle is a set of string replacements that cannot reach the state
machine, the hold timer, the `Idempotency-Key` wiring or the `pagehide` release — whereas *moving* five
steps and a live five-minute hold into new modules is real risk, taken to make a diff prettier.

The characterisation test went with it, and that is the honest cost: it existed to protect the
restructure, and its other justification (jsdom + Testing Library for the whole `ui/` library) is worth
doing on its own terms rather than smuggled in here. **The five-step flow and the hold are still
untested**, exactly as they were before this phase — recorded as a gap, not closed.

What did change there: `<Steps>` became numbered circles with checkmarks and keeps `aria-current="step"`;
the slot list became a `minmax` grid so times align in columns; the hold countdown moved onto the warning
tint with its `aria-live="polite"` intact; and every colour became `accent-*` rather than `brand-*`,
because this is the one screen that belongs to the tenant (§2.2).

**Added 2026-08-16: `<ThemeToggle />` in the header, beside the locale switcher.** The redesign gave
every screen a light and a dark rendering and a three-valued control to choose between them, and then
put that control only on the signed-in shells — `auth-header.tsx` and `dashboard-shell.tsx`. The
public booking page, which is the only screen most people using this product will ever see, rendered
whatever `prefers-color-scheme` asked for and offered no way to say otherwise: a customer on a
dark-by-default phone who wanted the light booking page could change it for their whole device or not
at all.

Nothing new was built. `ThemeToggle` already writes the `bam.theme` cookie the inline script in
`lib/theme-script.ts` reads before first paint, so the choice applies without a flash and survives
into the manage-booking screen and back. The two controls are now wrapped in one
`flex flex-wrap items-end gap-3`, which is the same arrangement `auth-header.tsx` uses — on a narrow
screen they wrap under the clinic's name rather than squeezing it.

This is chrome, not tenant content, and it is deliberately left on the neutral tokens rather than
moved to `accent-*`: §2.2's split is about what a tenant's brand colour may repaint, and a
system/light/dark select is ours.

### 3.4 The shims are gone

Done as its own step, after the rest was green. `dashboard-shell.tsx` went from **547 lines to 322** and
now exports exactly four things: `DashboardContext`, `useDashboardContext`, `useSignInRedirect`,
`DashboardShell`.

94 call sites moved to `components/ui/*`:

| from | to | count |
|---|---|---|
| `<input className={inputClass}>` | `<Input>` | 48 |
| `<select className={inputClass}>` | `<Select>` | 14 |
| `<textarea className={inputClass}>` | `<Textarea>` | 2 |
| `<button className={buttonClass}>` | `<Button>` | 15 |
| `<button className={secondaryButtonClass}>` | `<Button variant="secondary">` | 9 |
| `<Link className={buttonClass}>` | `<ButtonLink>` | 5 |
| `<a className={buttonClass}>` | plain `<a>` + `buttonRecipe()` | 1 |

The last row is the one that had to be decided rather than scripted: `subscription-screen.tsx`'s payment
link leaves the app for Stripe's hosted page, so it must stay an `<a>` and bypass the locale-aware router.
That is why `buttonRecipe()` survives the deletion of the constants — a recipe is for the element a
component cannot be.

**The `type` hazard did not materialise, and it was checked rather than assumed.** A bare `<button>`
defaults to `type="submit"` while `<Button>` defaults to `type="button"`, so a conversion could silently
stop a form submitting. Every one of the 24 converted buttons already carried an explicit `type`, and the
count of `type="submit"` across `apps/web/src` is **18 before and 18 after**. Element counts are likewise
conserved per file.

Two comments were rewritten rather than left pointing at deleted symbols — including the one in
`bookings-screen.tsx` recording a real past bug, where a secondary action built by appending overrides to
the primary class rendered white-on-transparent above an irreversible "Complete". That bug is now
structurally impossible: `cn()`'s `twMerge` drops the losing utility instead of leaving both to race in
stylesheet order.

### 3.5 The neutral ramp stays

§3's plan ended with "delete the `--color-slate-*` block". It is still there, on purpose. It is the
palette the semantic tokens are built from — deleting it replaces eleven named steps with eleven magic
oklch literals — and while it shadows Tailwind's stock slate, a `slate-500` typed out of habit lands on
the product's blue-tinted neutral instead of Tailwind's. That is a safety net, not debt.

### 3.2 Pre-existing defects fixed in passing

- **`app/not-found.tsx` never imported `globals.css`.** There is no root layout, so nothing above that
  file supplied a stylesheet, and every Tailwind class on the 404 screen was inert — it had been rendering
  unstyled since Phase 0. It now imports the stylesheet and carries its own copy of the theme script.
- **`components/locations-screen.tsx` began with a UTF-8 BOM**, now stripped and guarded by
  `src/encoding.test.ts`. **The associated mojibake report was wrong**: the em dashes in that file, including
  the user-visible `"—"` empty-address fallback, were always correct UTF-8. The corruption was in the
  *reading* — a tool opening a BOM'd file without `utf-8-sig` renders them as `â€”`. Recorded because the
  same false positive will otherwise be "found" again.

Two more came out of the first hands-on walk of the deployed app (2026-08-15), both on
`/{locale}/dashboard`:

- **The tenant dashboard had neither switcher.** `ThemeToggle` and `LocaleSwitcher` are rendered by
  `components/auth-header.tsx`, which is mounted on the signed-out site root and on the platform admin
  shell — and nowhere else. `DashboardShell` hand-rolls its own header, so a signed-in tenant user, who
  visits neither of those screens, could change neither theme nor language from inside the application.
  Both controls now sit in that header. The lesson is the general one: a control added to *the* header is
  only added to the headers that exist, and this app has two.
- **Every provider was told their own diary was archived.** The members table's Diary column read
  `providers.find(…) ?? t("diaryArchived")`, and the providers query is `enabled` only for a holder of
  `member:manage`. A `PROVIDER` holds `member:read` and not `member:manage`, so the list never loaded, the
  lookup always missed, and the fallback fired for every linked member on the screen. Not a redesign
  regression — it shipped with phase-9's provider onboarding — but it is what a real provider account saw
  first. The fix is in the type: the list reaches the column as `Provider[] | null`, `null` meaning *not
  fetched*, and the decision moved into a pure `lib/member-diary.ts` with `resolveDiaryState`. A diary
  missing **from** a list we hold is archived; not holding the list says nothing about it, and reports
  `diaryLinked` — "Linked" — instead. `[]` and `null` are now different answers, which is the whole bug.

**Increment 2 is the leverage.** The three class-name constants are redefined in terms of the new recipes
and marked `@deprecated`, and the old component names are re-exported from `./ui/*`. That commit changes
zero call sites and restyles the whole application. The constants are deleted in increment 8, once no file
imports them — never both in one step, because 14 files import them.

**Risk register.** `booking-flow.tsx` — 645 lines, five internal steps, and a live 5-minute hold, so the
state machine is *moved*, never rewritten, behind a characterisation test written first. `providers-screen.tsx`
— 1,169 lines, split into parts *before* restyling so the diff is readable. `app/not-found.tsx` — its own
`<html>` document above `[locale]`, cannot use `next-intl`, keeps its bilingual literals, and needs its own
copy of the theme script. `locations-screen.tsx` — carries a UTF-8 BOM and mojibake, including a `—` that
renders to users as the empty-address fallback.

# 4. Verification

## 4.1 Tests added

Each guards something this phase makes newly breakable — the same reasoning `i18n/routing.test.ts` already
uses when it reads the route directory off disk:

1. **`app/globals.contrast.test.ts`** — reads `globals.css`, parses the light block, the media block and the
   `[data-theme="dark"]` block, converts oklch → sRGB, and asserts every text pair ≥ 4.5:1 and every focus
   and border pair ≥ 3:1. It also **catches the deliberate duplication in §2.4 drifting apart**, which is
   otherwise invisible until someone reports it.
2. **`messages/messages.test.ts`** — `hu.json` and `en.json` hold identical key sets. Nothing enforced this
   before and this phase adds keys to both. Written *before* the keys.
3. **`lib/theme-preference.test.ts`** — cookie parsing, mirroring how `locale-preference` is used.
4. **A BOM guard** — no file under `src/` begins with U+FEFF.
5. **A characterisation test for the booking step machine** (increment 4).
6. **`lib/member-diary.test.ts`** — the regression suite for §3.2's "(archived diary)". It asserts the
   thing the original conflated: `providers: []` resolves to `archived`, `providers: null` to `linked`.
   No DOM needed, which is the point — the API was answering correctly throughout, so no API test could
   have caught it.

## 4.2 By hand

`i18n/routing.test.ts` is directory-sensitive. **This phase adds no route directory** — the theme is a
cookie, and the library sits under `src/components/`, not `app/`. If a `/styleguide` route is ever wanted,
`APP_SEGMENTS` gains it in the same commit; the test descends into route groups, so `(marketing)/pricing`
still needs `"pricing"` in the set.

Playwright and axe are deliberately **not** added here. tech-impl §39.6 already assigns end-to-end testing
to Playwright and none is installed; standing up a browser harness inside a redesign would swallow the
phase. §4.1's first test covers the deterministic half of WCAG. The rest is a manual walk — for each screen
in each theme: keyboard-only traversal reaching every action, a visible focus ring at every stop, the
`role="alert"` / `role="note"` / `aria-live` regions still announcing, no icon-only control without a
translated label, and **Hungarian strings not overflowing** — `hu` runs consistently longer than `en`, and
the dashboard navigation and the booking step rail are where it shows first.

# 5. Known limits

1. **`viewport.themeColor` can only key on `prefers-color-scheme`.** A visitor who forces light on a dark
   operating system gets dark browser chrome above a light page. There is no media feature for "this site's
   cookie", so this is not fixable, only recorded.
2. **The theme is applied by an inline script in `<head>`.** Reading the cookie in `[locale]/layout.tsx`
   instead would opt the whole locale layout into dynamic rendering, defeating `generateStaticParams` and
   `setRequestLocale`, and would still serve the wrong theme from a shared cache. No CSP header is set
   today; **if one is ever added, that script needs a nonce.**
3. **One hero image, not one per theme.** The obvious `<picture media="(prefers-color-scheme: dark)">` is
   wrong here for the same reason as (1) — a media query cannot see `data-theme`, so a visitor forcing
   light on a dark OS would get the dark hero under light chrome. One image, tinted in CSS by a
   `--surface`-derived overlay that flips with the theme. `public/hero-booking.jpg` is that image: 1376×768,
   67 KB, abstract, no text, no faces, and deliberately industry-neutral so it is not wrong for a
   barbershop or a law practice. It is a JPEG rather than a WebP because no image tooling is installed on
   this machine; re-encoding is a worthwhile ten-minute job, not a blocker.
4. **Per-tenant branding is plumbing only** (§2.2). The indirection exists; nothing reads tenant data yet.
