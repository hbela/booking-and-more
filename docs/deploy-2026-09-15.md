The compose `migrate` service is built from this release's API image and runs `prisma migrate deploy` in `/app/packages/db`. Both API and worker depend on its successful completion. Expect the migration container to exit with code 0; its stopped state is intentional.

Do not manually run `migrate dev`, `db push` or reset commands on production. If migration fails, inspect the migration logs and database state before retrying; do not mark it applied merely to allow startup.

To inspect status from the release API container terminal:

## 7. Rollback

If migration fails, stop the rollout and investigate before starting the new API. If code is unhealthy after successful migration, redeploy the recorded previous revision/images through the same Coolify resource, retaining the database and Redis volumes.

The two migrations introduced here are additive, so the previous application can normally run with these extra columns left in place. Verify compatibility against the actual previous production revision and any other pending migrations first. Do not drop the new columns to perform a routine code rollback.

A database restore is the last resort for data damage, not the default rollback: it loses writes since the backup. Stop API/worker writes and assess those writes before restoring. Stripe configuration and external payment links are not rolled back by restoring the app or database; use the recorded billing configuration to handle them separately.
